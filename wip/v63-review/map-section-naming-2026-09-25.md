## 4. lite/ 與 tools 對 xref 文字格式的依賴（確定，讀原始碼）

- **`tools/build_lite.py` 的 `rewrite_links(s, ctx)`（行 443–479）強依賴 xref 前後文的精確格式**：
  - `xref = r'<a\b[^>]*class="xref"[^>]*>.*?</a>'`（行 444）
  - 行 460：`re.sub(r'第\s*((?:%s)(?:\s*、\s*%s)*)\s*節' % (xref, xref), grp, s)` — 只認得 `第 <xref>(、<xref>)* 節` 這個精確模板（含多節用頓號並列），命中就轉成 `完整版〈標題〉、〈標題〉`。
  - 行 461：`re.sub(r'「\s*(%s)\s*」' % xref, ...)` — 只認得 `「<xref>」`（引號包住單一 xref，如「十分鐘看完」那種 PHRASE_LINK 類型），轉成 `完整版〈標題〉`。
  - 行 462：任何沒被上面兩條規則吃掉的 xref，一律轉成 `完整版〈標題〉`（用連結文字或節名 fallback）。
  - **推論（疑似，依程式邏輯）**：`〈標題〉` 這個尖角括號寫法（第 3 類第 2 項，全檔只有 2 處人工手打的）正好是這支腳本產生 lite 版時的輸出格式；若把「節「標題」」的直角引號改成尖角括號，或反過來，不會讓程式壞（因為腳本是靠 `class="xref"` 抓，不是靠引號符號本身判斷），但生出來的 lite 版文字風格會與現有的 2 處人工〈〉重複／不一致，值得主線留意。
  - 行 464–476 的 `other()`：任何 `href="#…"` 但不是 `xref` class 的站內連結（如 toc 連結），直接剝成純文字，不保留 title。
- **`tools/v7_check.py` 的 `cmd_anchors`（行 465–485）**：只做結構檢查——`before` 的所有 id 是否還在 `after` 裡（`gone`），`after` 的所有 `href="#…"` 是否都能解析到存在的 id（`broken`）。**不檢查、也不關心 xref 周圍的文字格式**（不管是「第N節」「（第N節）」還是「見第…」，只要 href 對得到 id 就算過）。
- **`tools/guidetools.py`**：grep `xref` 沒有命中任何函式定義或規則（只有 `section_of`／`ChapterCtx`／`rewrite_links` 等在 `build_lite.py`，不在 `guidetools.py`）。`guidetools.py` 本身沒有 xref 相關的檢查邏輯，該檔可能是別的用途（`section_of`、DOM 輔助），未見與本任務相關的規則。
- **`lite/` 目錄**：內含 `index.html`（build_lite.py 的輸出）、`manifest.json` 等資料檔，是 build_lite 的產物；未見另外的原始碼在 `lite/` 內對 xref 文字做二次解析（`lite/` 底下無 .py，只有資料與靜態頁）。

## 5. 主線要決定的事

- 全書「第 N 節」引用有無標題（367 無標題 vs 49「」有標題 vs 2〈〉有標題）三種比例懸殊的寫法並存，要不要統一，以及統一成哪一種會牽動 `build_lite.py` 行 460–462 的 regex 是否要跟著調整。
- 多節並列時（如「第 6、7 節」）有些後續節號有包 `<a class="xref">`、有些沒包（見分類第 4 類「其他接續」42 處與各「其他數字連結」子類），這種「部分節號沒連結」的寫法本身是否要統一成每個節號都連結。
- 「（第 N 節）」括號式與「第 N 節」不帶括號式目前混在同一個 367 大類裡沒有拆開統計，是否要單獨列一類決定寫法。
- 「本節／上面／下面／前面／後面」這類相對稱呼共 233 次（未濾重複與 CSS/註解雜訊），是否要收斂成統一句式（例如都改成「見第 N 節」），以及這類相對稱呼在改版、搬動內容順序時容易跟著失真的風險。
- 〈標題〉尖角括號的寫法只有人工打過 2 次，剛好與 `build_lite.py` 自動產生 lite 版時用的符號撞在一起，統一時要注意這個巧合是否造成混淆。
- 「見第…」這個樣式我的規則分類裡沒抓到獨立次數（被併入其他類），若要精確統計「見第」開頭的寫法，需要另外單獨 grep 確認，本次未單獨列出。
